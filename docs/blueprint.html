How the pieces sit

Postgres is the only thing that decides whether a seat is free. Redis carries job queues and the socket fan-out — never a lock. Two sources of truth for one seat is how a system sells the same chair twice.

The seat lifecycle

Four states. The two amber transitions are the automatic ones — nobody clicks anything to make them happen, and they are the two the brief cares most about.

The race, and the lock that ends it

Two customers, one seat, requests landing microseconds apart. The naive version has no error anywhere in the logs — it just quietly sells the chair twice.

check, then writeRACE
// both requests read AVAILABLE,
// both write HELD, second one wins
// silently. No error is ever raised.

const seat = await prisma.showSeat
  .findUnique({ where: { id } });

// ← another request interleaves here

if (seat.status === 'AVAILABLE') {
  await prisma.showSeat.update({
    where: { id },
    data:  { status: 'HELD' },
  });
}

await prisma.$transaction(async (tx) => {
  await tx.$queryRaw`
    SELECT id FROM "ShowSeat"
    WHERE id = ANY(${seatIds})
    ORDER BY id
    FOR UPDATE`;

  // contender #2 blocks right there,
  // wakes up, reads HELD, gets a 409

  assertAllFree(tx, seatIds);

Why ORDER BY id

Two customers grabbing seats A and B in opposite orders deadlock. Postgres resolves a deadlock by killing one transaction — which turns a clean "that seat just went" into a 500. Sorting the lock set makes the deadlock impossible rather than merely unlikely.

Waitlist, end to end

A genuine sequence, so it is numbered. Steps 4 and 5 loop until someone accepts or the queue runs dry — and both loops re-enter the same advanceWaitlist() function, never a second copy of it.

  1. Category sells out, customer joins the queue

    POST /shows/:id/waitlist writes one WaitlistEntry with joinedAt. Duplicate entries are refused, so refreshing the page does not buy three places in line.

  2. Somebody cancels

    The booking is marked CANCELLED and each freed seat is passed to advanceWaitlist(showSeatId) — inside the same transaction that freed it.

  3. The queue is read, FIFO, one row at a time

    ORDER BY joinedAt ASC LIMIT 1 FOR UPDATE SKIP LOCKED. Earliest wins; a concurrent cancellation skips the locked row instead of offering the same seat twice.

  4. Seat goes OFFERED, email goes out

    Seat and entry both get offerExpiresAt. The entry gets an offerToken — 32 bytes from crypto.randomBytes, never Math.random(). The emailed link is that token; it is a bearer credential for a real seat.

  5. They accept — or the clock runs out

    Accepting checks all five: token matches, entry is OFFERED, not expired, seat still OFFERED, and the caller is the customer it was offered to. Silence instead means the sweeper marks the entry EXPIRED and feeds the seat straight back into step 3.

  6. Queue empties

    No one left waiting → the seat returns to AVAILABLE and the map updates for everyone watching the show.

Where state lives

A chair does not know whether it is sold. Seat is physical geometry, written once per venue. ShowSeat is one row per seat per show, and it is the only thing that carries status.

Never leaves the server

heldByUserId is not in any client payload. The public map shows that a seat is held; it must never show who is holding it. Every seat response is an explicit select, not a spread of the row.

Standing rules

Decisions already made. Changing any of them is a conversation, not a commit — they are the ones that quietly cost a day if reversed halfway.

  1. 01
    Postgres is the only source of truth for seat state. Never a Redis lock.
  2. 02
    Every state transition sits inside a transaction that opens with FOR UPDATE. No check-then-write.
  3. 03
    Cancellation and offer-expiry call the same advanceWaitlist(). Never two copies.
  4. 04
    Lazy expiry is the correctness guarantee; the sweeper is only what makes it feel live.
  5. 05
    Email is queued through BullMQ. A confirmed booking never waits on SMTP.
  6. 06
    POST /auth/register hard-codes the role server-side. No request shape accepts one.
  7. 07
    offerToken and qrToken are crypto.randomBytes(32). Both are bearer credentials.
  8. 08
    JWT algorithm pinned to HS256 on both sign and verify. Never inferred from the token.
  9. 09
    Broadcast after commit, never inside the transaction.
  10. 10
    DATABASE_URL pooled for the app, DIRECT_URL unpooled for migrations. Mixing them is the classic deploy break.
  11. 11
    Claude commits; only the repo owner pushes.
